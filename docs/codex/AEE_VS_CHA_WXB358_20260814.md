## AEE Behaviour

### Confirmed runtime behaviour

The loaded AEE page provides these browser globals:

* `mcs8Client`;
* lowercase `openvideo`;
* `closeVideo`;
* `displayVideoFrame`;
* the page's video WASM runtime.

The AEE Monitor product assigns a permitted device to a tile and mounts a
`PlayCtl` component. That component calls:

```text
client().openVideo(playId, videoElement, channel, serverId)
```

The inspected SDK wrapper converts that call into a receive-only
`mediaMonitor` request with video `streamType=2`. The observed AEE Monitor UI
and its current product source did not expose a stream-profile selector.
This confirms the parameter currently used by both AEE and CHA, but does not
establish what every possible `streamType` value means or whether another
supported profile-selection API exists.

The loaded AEE/MCS8 SDK handles `newConsumer` in two different ways:

1. When `rtpParameters.codecs` contains H.265, it places the current media
   token into `appData`, calls the page-global lowercase
   `openvideo(appData, ShowRemoteObj)`, and returns without creating the normal
   WebRTC consumer.
2. Otherwise, it calls `consumerTransport.consume(...)`, creates a
   `MediaStream`, and assigns the track to `video.srcObject`.

The AEE page-global lowercase `openvideo` is page-specific glue. It opens a
same-origin `/mediaStream` WebSocket with media parameters, invokes the page's
WASM video decoder, and renders decoded frames to a Canvas. `closeVideo`
removes the Canvas and closes the WASM video pipeline.

### Current live-static comparison

The current AEE static assets were downloaded read-only on `2026-08-14` and
compared locally with the CHA release assets. Only source files and hashes were
examined; no credential or media payload was saved.

* Current AEE `/static/mcs8Client.js`:
  SHA-256
  `EE46531FF864BCF730D85502B994C26D273F556DD733812EF6BAB6E8373D9897`.
* CHA vendored `mcs8Client.js`:
  SHA-256
  `ABD0E09A8DC9656C4E3A3955700D3A4E4ECA7BF51BD52252CF1008D7A3AF42BB`.
* The two SDK bundles differ by exactly one 27-character condition. The current
  AEE bundle only uses `mediaHttpProxy` when the media-server record also has

* The lowercase `openvideo(...)` H.265 branch is therefore present and
  otherwise identical in both the current live AEE SDK and the CHA vendored

The current AEE H.265 page runtime consists of:

  `libstream_process.js` and `webgl.js`
  (`F3A57533FFBE5EDD1F1626CAC1F87532581C95F3522B79A6A2328F973C283974`);
* `libstream_process.js`, an Emscripten runtime that loads
  `libstream_process.wasm` and exports `_open_video` and `_close_video`
  (`714791ABD5BE05F23D4A5C8EB51764532E116CD99F3D936B9A7A434C1A9CB14C`);
* `webgl.js`, which renders decoded YUV frames to a Canvas using WebGL.
  Its SHA-256 is
  `1E08BA7F4A2E7C9252BCD18948AF97C75EADACF9216FF866D346FA851B9E5759`;

  `E2B11EAE991C49697D888144B760A9472C2EB21BF04C0811991CB38F93645073`.

The inspected `openvideo` function builds a same-origin `/mediaStream`
WebSocket URL containing the device, channel, play identifier and media token,
then passes it to `Module._open_video`. The same page glue also logs the
complete `videoParam` object to the browser console. These behaviours reinforce
that the AEE page implementation is **Class D / Reference Only**: directly
copying it into CHA would violate the CHA credential and logging boundary.

The SDK's only verified live-vs-vendored difference is the
`mediaHttpProxy`/SSL guard. It is unlikely to explain this Canary failure
because the failed CHA run had already connected Gateway and Media WebSockets,
joined the room and reached `openVideo` before the browser raised
`openvideo is not defined`. This is an evidence-based inference, not a claim
that SDK drift can be ignored generally.

### Static stream/profile surface

The current live SDK and the byte-equivalent CHA vendored SDK expose this
public monitoring method:

```text
openVideo(devId, showObject, channelId, serverId)
```

It has no codec or profile argument and always constructs a video
`mediaMonitor` request with `streamType=2`. The lower-level
`mcs8MediaClient.openVideo(...)` passes a supplied `streamType` through to the
server, but the public wrapper exposes no supported way to select another
value. In the bundle, the only literal meanings that can be established are:

* `2` for live video monitoring/sending;
* `0` for audio;
* `-1` for playback operations.

No alternate live-video stream value, device codec/profile selector or
device-specific capability query was found in the current SDK surface. Browser
and router RTP-capability methods do exist, but they do not establish which
codec/profile a particular monitored device will produce.

Therefore the static SDK does **not** currently prove that an H.264
stream/profile can be selected for `WXB358`. Calling lower-level internals with
an invented `streamType` would be protocol guessing and private-SDK coupling,
so it is not an approved experiment without AEE evidence or upstream protocol
documentation.

### Authorized device comparison

#### WXB353 control

The authorized AEE page opened `WXB353` through the normal UI:

* request: `mediaMonitor`, `kind=video`, `streamType=2`;
* request result after `53 ms`: `status=opened`;
* `newConsumer` codec:
  * `video/H264`;
  * `profile-level-id=42e01f`;
  * `packetization-mode=1`;
  * `level-asymmetry-allowed=1`;
  * RTX associated with the H.264 payload;
* AEE used the normal WebRTC consumer/`MediaStream` path;
* lowercase `openvideo` was not called;
* `loadedmetadata`, `loadeddata`, `canplay` and `playing` occurred approximately
  `1.825 s` after the `mediaMonitor` request;
* rendered resolution: `1920 × 1080`;
* video track: `live`, unmuted;
* a second close/open cycle succeeded with the same H.264 profile and
  resolution.

Closing the tile sent the normal video and audio `closeMediaMonitor` requests;
each returned successfully in approximately `56–57 ms`. The video track became
`ended`, the tile was removed and the SDK show-video map returned to zero.

The current AEE SDK retained ended consumer objects in its internal
`_consumerList` with `closed=false` after tile close and after navigation back
to the GIS page. This is an observed AEE page/SDK bookkeeping behaviour, not
proof that the upstream producer remained open: `closeMediaMonitor` succeeded,
the tracks ended and no tile remained. CHA should retain its existing stronger
explicit cleanup requirements rather than copy this lifecycle detail.

#### WXB358 target

At the same time and under the same authorized account/browser/network:

* AEE `DevTree` reported:
  * `online=1`;
  * `status=1`;
  * device-level `enableVideo=true`;
  * `alarm=205` (the current AEE language map labels this as low battery);
* the target node was draggable and the AEE page accepted the UI drop;
* AEE sent `mediaMonitor`, `kind=video`, `streamType=2`;
* the Media request rejected in approximately `51–67 ms` with:
  `devices is offline request.method "mediaMonitor"`;
* the AEE page retried `mediaMonitor` approximately every three seconds;
* the tile displayed `Unable to play`;
* no `newConsumer` arrived;
* no device-specific `rtpParameters` or codec/profile was delivered;
* lowercase `openvideo` was not called;
* no `/mediaStream` fallback was opened;
* no video track, Canvas frame or first frame was produced.

Closing the failed tile sent `closeMediaMonitor`; the requests returned
successfully, the show-video map returned to zero, the tile was removed and no
new consumer had been created for `WXB358`.

This establishes a current AEE backend/device-state inconsistency: the
management device tree says online, while the Media service rejects monitoring
as offline. The low-battery alarm is recorded context, but the evidence does
not prove that it caused the Media rejection.

## Difference

### Confirmed

* AEE's product page supplies a lowercase `openvideo` H.265 fallback runtime.
* CHA's product page does not supply that page-global runtime.
* The SDK path used by CHA can therefore raise `openvideo is not defined` if
  an H.265 `newConsumer` is delivered.
* The current live AEE SDK retains the same H.265 fallback branch as the CHA
  vendored SDK; the known SDK drift is confined to a media-proxy SSL guard.
* CHA's normal H.264 WebRTC consumer path has already been validated with six
  real devices.
* In the authorized same-session AEE control, `WXB353` opened as H.264
  `42e01f`, produced a 1920 × 1080 live track in approximately 1.825 seconds
  and closed successfully.
* In the authorized same-session AEE target test, `WXB358` failed at
  `mediaMonitor` with `devices is offline` before any `newConsumer` or codec
  information existed.
* The current AEE test therefore does not reproduce a current H.265 fallback
  for `WXB358`, and it does not show a current CHA-only playback failure.

### Not yet confirmed

* The actual `WXB358` codec and RTP profile in AEE.
* Whether AEE can render `WXB358` after the Media service again recognizes the
  device as available.
* Whether MCS8 exposes a documented or server-supported H.264 stream/profile
  selection that avoids the page-specific H.265 fallback. No such public
  selector was found statically in the current SDK.
* Whether a secure, supported H.265 adapter can be used without exposing a
  reusable AEE credential to the CHA browser.

## Capability Classification

* **Class A — Backend Read-only Capability:** device online state, device
  metadata and safe capability/profile discovery.
* **Class B — SDK / Protocol Media Capability:** `newConsumer`,
  `rtpParameters`, codec/profile selection, normal WebRTC consumption and any
  supported H.265 media protocol.
* **Class C — CHA Business Aggregation:** CHA session ownership, Canary
  isolation, 1/4/6 layout, lifecycle state, telemetry and resource cleanup.
* **Class D — Reference Only:** AEE Monitor page state, drag/drop UI,
  page-global glue and private page integration. These must not become a CHA
  production runtime dependency by copying the page.

The current target failure is classified as **Class A / upstream device-state
evidence** until a successful Media open produces Class B codec evidence. The
historic `openvideo is not defined` path remains a potential Class B CHA gap,
but it must not be treated as the current device state.

## Conclusion

The origin of `openvideo is not defined` remains confirmed at source level:
both the current live AEE SDK and the CHA vendored SDK have a unique lowercase
`openvideo` call in the H.265 `newConsumer` branch, while CHA does not provide
the AEE page-global fallback.

The authorized AEE comparison has now shown that, during the current test
window, `WXB358` fails earlier: the Media service rejects `mediaMonitor` as
offline and sends no `newConsumer`. Therefore the historic Production Canary
and the current AEE test represent different upstream device states or time
windows. It remains a strong hypothesis that the historic Canary received an
H.265 consumer, but it is still not acceptable to mark
`WXB358 codec=H.265` as verified.

No CHA media-code change is justified by the current test. The next
device-specific comparison must occur when `WXB358` is accepted by the AEE
Media service.

## Decision

* Keep production Realtime disabled.
* Do not define a blind `openvideo` shim.
* Do not copy AEE's token-bearing page glue into CHA.
* Do not introduce FFmpeg, a media server, SFU, custom decoder, transcoding or
  a protocol workaround.
* Implement the smallest independent Class C error-handling correction:
  * normalize the observed upstream `devices is offline` rejection to the
    CHA-owned `DEVICE_MEDIA_OFFLINE` error code;
  * return a user-facing CHA message rather than the raw AEE error;
  * issue a compensating `closeVideo` when `openVideo` rejects, so the proxy's
    authorized-monitor state and upstream monitor request are closed
    symmetrically;
  * preserve all unrelated upstream errors unchanged.
* The Class C correction does not select a codec, change `streamType`, add an
  AEE probe or claim to fix the historic H.265 path.
* Do not create a CHA H.265 adapter from the historic error alone.
* First restore or wait for `WXB358` Media availability, then repeat the same
  authorized AEE single-device test.
* If a `newConsumer` is then delivered, capture its sanitized codec/profile,
  RTP parameters, first-frame path and close/release evidence.
* Only if the online-device comparison confirms a CHA-only Class B gap should
  a minimal supported SDK/Protocol Adapter be designed.

The Class C correction is covered by a Node runtime test and the Python test
suite. Current results:

* JavaScript syntax checks: PASS;
* runtime normalization/compensating-close test: PASS;
* V2 test suite: `73 tests PASS`.
